Diseñar un asistente local con IA

Tres equipos, tres problemas reales y un mismo desafío: crear un sistema útil basado en un modelo de lenguaje que funcione localmente, tenga una especialización definida y pueda manejar información entre conversaciones.

1 · Introducción sombrilla

Los modelos de lenguaje pueden responder preguntas, pero un sistema de IA requiere algo más: un propósito, instrucciones especializadas, un entorno de ejecución, pruebas y un mecanismo para conservar o consultar información relevante. En este proyecto cada equipo diseñará y evaluará un asistente para un problema concreto.

Trabajaremos con Ollama (ejecuta modelos locales), Qwen3:4B (modelo inicial sugerido) y Open WebUI (interfaz y configuración). Los equipos podrán justificar otro modelo local compatible. No se requieren APIs comerciales, suscripciones ni agentes autónomos.

Principio de investigación: que una opción aparezca en la interfaz no significa que funcione. Toda capacidad —en especial la memoria automática— debe demostrarse con evidencia. Versión preliminar: la memoria automática no es requisito ni se evaluará por ahora. Investigaremos su viabilidad durante el semestre.

2 · Los tres problemas

OPCIÓN A

Tutor inteligente

Problema: un tutor no recuerda dificultades ni avances del estudiante.

Producto: tutor de una materia delimitada que explica, ofrece pistas, verifica comprensión y adapta la ayuda.

Continuidad opcional a explorar: conocimientos previos, errores frecuentes y progresos, evitando datos sensibles.

Demo: aprendizaje en un chat y adaptación en otro.

OPCIÓN B

Asistente de investigación

Problema: objetivos, decisiones y resultados de un proyecto se dispersan.

Producto: asistente que analiza materiales, registra decisiones y organiza próximos pasos.

Continuidad opcional a explorar: objetivos, decisiones vigentes y cambios de rumbo.

Demo: recuperar y corregir una decisión en un chat posterior.

OPCIÓN C

Asistente de decisiones

Problema: las recomendaciones de un chatbot pueden ser inconsistentes o poco explicables.

Producto: sistema que compara opciones con criterios explícitos y justifica su recomendación.

Continuidad opcional a explorar: preferencias y restricciones que pueden cambiar.

Demo: modificar una restricción y explicar cómo cambia la decisión.

Cada equipo elige una opción sin repetirla, o propone otra alternativa para aprobación del profesor.

3 · Instrucciones generales

  1. Formen equipos de dos o tres integrantes y elijan un problema.
  2. Definan un usuario concreto, un alcance razonable y dos o tres funciones principales.
  3. Instalen un LLM local y demuestren que responde sin usar una API de pago.
  4. Creen en Open WebUI un modelo personalizado y una skill o conjunto reutilizable de instrucciones especializadas. Si la versión instalada no presenta una función denominada «Skills», documenten una alternativa equivalente mediante instrucciones del modelo y archivos de conocimiento.
  5. Como actividad opcional, prueben la continuidad entre conversaciones mediante un archivo ESTADO.md. La memoria automática no es requisito.
  6. Realicen pruebas con resultados observables, registren fallos y mejoren el diseño.
  7. Entreguen archivos, instrucciones reproducibles y una demostración en vivo.

Ética y privacidad: utilicen datos ficticios o autorizados. No introduzcan expedientes reales, contraseñas, información médica o datos personales sensibles. El sistema debe indicar incertidumbre y permitir corregir o borrar información almacenada.

4 · Guía de instalación paso a paso

Se recomiendan 16 GB de RAM para trabajar con mayor comodidad, aunque el rendimiento depende del equipo. Reserven espacio para descargar varios gigabytes de modelo y dependencias. Comiencen con qwen3:4b; si el equipo no lo soporta adecuadamente, consulten antes de cambiar de modelo.

Paso A · Windows: instalar Ollama y Qwen
  1. Descarguen Ollama desde ollama.com/download y elijan Windows.
  2. Instalen y ejecuten Ollama. Abran PowerShell.
  3. Comprueben la instalación:
    ollama --version
  4. Descarguen el modelo:
    ollama pull qwen3:4b
  5. Inicien una conversación local:
    ollama run qwen3:4b
    Escriban una pregunta en español. Para salir, utilicen /bye.
  6. Comprueben que aparece en la lista:
    ollama list

Si PowerShell no reconoce ollama, ciérrenlo y ábranlo nuevamente; verifiquen que Ollama esté instalado y ejecutándose.

Paso B · macOS: instalar Ollama y Qwen
  1. Descarguen Ollama desde ollama.com/download y elijan macOS.
  2. Instalen y abran la aplicación.
  3. Abran Terminal y ejecuten:
    ollama --version
ollama pull qwen3:4b
ollama run qwen3:4b
  4. Escriban una pregunta de prueba; salgan con /bye y verifiquen:
    ollama list
Paso C · Windows y Mac: instalar Open WebUI con Docker (ruta recomendada)
  1. Descarguen Docker Desktop. En Windows puede requerirse WSL 2 y virtualización habilitada. Sigan las instrucciones del instalador y reinicien si se solicita.
  2. Abran Docker Desktop y esperen a que indique que está ejecutándose.
  3. En PowerShell (Windows) o Terminal (Mac), comprueben:
    docker --version
  4. Generen una clave local larga y guárdenla en un lugar seguro. Sustituyan CAMBIA_ESTA_CLAVE_LARGA por esa clave en el siguiente comando. Ejecuten todo en una sola línea:
    docker run -d -p 3000:8080 --add-host=host.docker.internal:host-gateway -v open-webui:/app/backend/data -e WEBUI_SECRET_KEY=CAMBIA_ESTA_CLAVE_LARGA --name open-webui --restart always ghcr.io/open-webui/open-webui:main
  5. Esperen a que termine la descarga y abran http://localhost:3000 en el navegador.
  6. Creen la cuenta administradora local. Conserven su contraseña.
  7. Si el servicio no responde, revisen:
    docker logs open-webui

Importante: el volumen open-webui conserva conversaciones y configuraciones. No lo borren durante el proyecto. La dirección localhost solo funciona en la propia computadora.

Alternativa para macOS: Open WebUI con Python, sin Docker

Úsenla si Docker resulta demasiado pesado. Esta es la ruta ensayada en el entorno del profesor.

  1. Instalen Homebrew si no está disponible.
  2. En Terminal, ejecuten:
    brew install python@3.11
mkdir -p ~/open-webui
cd ~/open-webui
"$(brew --prefix python@3.11)/bin/python3.11" -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install open-webui
open-webui serve
  3. Abran http://localhost:8080. La primera carga puede tardar.
  4. Para reiniciar en otra sesión:
    cd ~/open-webui
source .venv/bin/activate
open-webui serve

Open WebUI admite Python 3.11/3.12 según su guía actual. Eviten mezclar la instalación con el Python del sistema.

Problemas frecuentes de instalación
  • Docker no arranca en Windows: comprueben requisitos de WSL 2 y virtualización; consulten la guía oficial de Docker.
  • Puerto 3000 ocupado: sustituyan -p 3000:8080 por -p 3001:8080 al crear el contenedor y abran localhost:3001.
  • No aparece Qwen: comprueben ollama list, que Ollama esté ejecutándose y la conexión de Open WebUI a Ollama.
  • Open WebUI en Docker no conecta a Ollama: revisen Settings → Admin → Connections; la dirección típica del host es http://host.docker.internal:11434. En instalaciones Python suele ser http://localhost:11434. Consulten la documentación oficial de conexión.
  • Modelo lento: cierren programas pesados y documenten RAM, CPU/GPU y tiempos. No cambien silenciosamente el modelo.

5 · Configurar el asistente, su especialización y su memoria

Configuración inicial de Open WebUI
  1. En Open WebUI, abran un chat nuevo y seleccionen qwen3:4b. Comprueben que responde.
  2. Entren en Workspace → Models. Esta sección puede mostrar 0 Models aunque Qwen ya funcione: allí se administran los modelos personalizados.
  3. Elijan Create, asignen un nombre al asistente y seleccionen qwen3:4b como Base Model.
  4. Escriban instrucciones claras: rol, audiencia, límites, tono, proceso de respuesta y cuándo reconocer incertidumbre.
  5. Guarden y comprueben que el nuevo asistente aparece en el selector del chat.
  6. Si su versión ofrece Function Calling, configuren Native para probar herramientas. Comprueben las capacidades o herramientas disponibles en el modelo y en el chat; la ubicación exacta puede variar por versión.
Crear y probar una skill

Para este proyecto, una skill es un procedimiento reutilizable y especializado que dirige cómo debe actuar el asistente. No es simplemente darle un nombre al chatbot.

  1. Escriban un archivo skill.md con las secciones Propósito, Cuándo usarla, Pasos, Restricciones, Formato de salida y Ejemplo.
  2. Integren ese procedimiento mediante la función Skills, si está disponible en su versión, o mediante instrucciones del modelo personalizado y archivos de conocimiento.
  3. Prueben una tarea que active la especialización y otra que no deba activarla.
  4. Guarden el archivo original y capturas o transcripciones de las pruebas.
# Skill: tutor con pistas
## Propósito
Ayudar a comprender conceptos sin entregar inmediatamente la solución.
## Cuándo usarla
Cuando el estudiante pida ayuda con un ejercicio.
## Pasos
1. Preguntar qué ha intentado.
2. Dar una pista breve.
3. Verificar comprensión.
4. Ofrecer otra pista si hace falta.
## Restricciones
No inventar resultados ni asumir que el estudiante aprendió.
## Formato
Pista → pregunta de comprobación → siguiente paso.
Continuidad entre sesiones mediante archivo de estado (opcional)

No se exige memoria automática. Como experimento voluntario, pueden pedir al chatbot una instantánea del proyecto y guardarla ustedes en un archivo Markdown. Esto no requiere herramientas ni API.

  1. Al terminar una conversación, envíen el comando de abajo.
  2. Copien la respuesta a un archivo local llamado ESTADO.md. El chatbot no crea el archivo automáticamente por el simple hecho de recibir el comando.
  3. En un chat nuevo, adjunten el archivo o peguen su contenido.
  4. Cuando cambie una decisión, generen un nuevo estado y sustituyan el archivo anterior.

Comando para guardar el estado:

Genera una instantánea del estado actual del proyecto en Markdown,
para guardar como ESTADO.md. Incluye:
1. Propósito y alcance.
2. Decisiones vigentes y justificación.
3. Funciones comprobadas y evidencias.
4. Problemas abiertos y limitaciones.
5. Próximos tres pasos.
6. Información no confirmada.
No inventes datos, señala contradicciones y evita datos sensibles.
Devuelve solamente el contenido de ESTADO.md.

Comando para reanudar:

Este es el estado guardado del proyecto. Úsalo como contexto,
no como prueba infalible. Resume dónde quedamos, señala dudas
y pregúntame cuál es la siguiente tarea.
[Adjuntar ESTADO.md o pegar su contenido]

Prueba opcional: verifiquen en un chat nuevo que recupera las decisiones, corrijan una y actualicen el archivo. Se trata de continuidad asistida por archivo, no memoria automática.

7 · Entregables finales

Un integrante subirá a Canvas un ZIP por equipo antes del cierre del domingo 6 de diciembre. Debe contener:

  • README.md o PDF: propósito, integrantes, problema y funciones.
  • INSTALACION.md: instrucciones reproducibles para instalar y configurar el sistema.
  • skill.md y demás instrucciones especializadas.
  • Configuración exportable del asistente, cuando Open WebUI permita exportarla; de lo contrario, capturas y pasos exactos para reconstruirla.
  • PRUEBAS.md o PDF: al menos cinco casos con entrada, resultado esperado, resultado observado y conclusión.
  • Si realizaron la actividad opcional, incluyan el archivo de estado y una breve prueba de recuperación en otro chat.
  • LIMITACIONES.md: errores, riesgos, privacidad, dependencias y posibles mejoras.
  • Capturas o grabación breve de respaldo para el caso de una falla durante la demostración.

Demostración del 7 de diciembre: propongo 10–12 minutos por equipo, más preguntas. Deben mostrar el sistema funcionando, ejecutar una tarea real y explicar su skill. La memoria automática no se exige en esta versión preliminar. Todos los integrantes deben poder explicar las decisiones principales.

8 · Criterios de evaluación

La calificación de las etapas seguirá los pesos del calendario. Dentro de cada entrega se valorará: funcionamiento verificable, claridad del diseño, especialización útil, calidad de las pruebas, análisis crítico y reproducibilidad. Una respuesta convincente del chatbot sin evidencia de ejecución no se considerará prueba suficiente.

El uso de IA para apoyar el desarrollo está permitido. Los estudiantes deben declarar qué herramientas utilizaron, para qué y qué decisiones verificaron personalmente.

Etapa 1 · Propuesta del proyecto

Entrega: lunes 26 de octubre de 2026 · Extensión: 1–2 páginas · Formato: PDF · Modalidad: un documento por equipo.

Propósito: definir qué problema resolverán, a quién ayudará el sistema y qué funciones concretas tendrá. No se requiere todavía instalar software, escribir código ni presentar un prototipo.

1. Título e integrantes

Incluyan el nombre provisional del proyecto y los nombres de todos los integrantes.

2. Problema que desean resolver

Describan una necesidad concreta: ¿qué dificultad existe, por qué importa y qué limitaciones tienen las soluciones actuales? Eviten afirmaciones vagas como «hacer un chatbot que ayude a las personas».

3. Usuarios

¿Quién utilizará el asistente? Identifiquen un grupo específico, sus necesidades y en qué situaciones utilizará el sistema.

4. Objetivos

Escriban un objetivo general y, si resulta útil, dos o tres objetivos específicos. Un objetivo describe qué se quiere lograr.

5. Funcionalidades (2–3)

Para cada función expliquen: (a) qué solicita o proporciona el usuario; (b) qué hace el sistema; (c) qué recibe el usuario. Deben ser funciones que luego podamos probar.

Ejemplo · Tutor de Java

Problema: estudiantes principiantes necesitan practicar fuera de clase y recibir orientación adaptada a sus dificultades.

Usuarios: estudiantes universitarios que comienzan a programar en Java.

Objetivo: apoyar el aprendizaje de conceptos básicos de Java mediante un tutor local.

  1. Explicar: recibe una pregunta y ofrece una explicación breve con un ejemplo adecuado al nivel.
  2. Practicar: recibe un tema y propone ejercicios de dificultad progresiva.
  3. Orientar: recibe una solución, identifica errores y ofrece pistas sin revelar inmediatamente la respuesta.

Distinción clave: «ayudar a aprender Java» es un objetivo; «generar un ejercicio y ofrecer pistas» es una funcionalidad verificable.

Evaluación: claridad, pertinencia y viabilidad. La propuesta podrá ajustarse durante el proyecto en consulta con el profesor. No se exige memoria automática en esta etapa.
